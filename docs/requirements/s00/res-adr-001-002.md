# ADRへの回答と確認

## ADR-001-java-in-devcontainer.md

### 1. DevContainer 内でローカル APK ビルドを行う予定はありますか？
- 開発が進んできた段階で、エミュレーターによるテストでは把握できない問題（ステータスバーやOSナビゲーションボタンとのUI競合など）の調整に、実機テストを行いたい
- その際、Expoクラウドビルドだと、回数制限とキュー待ち時間がネックになるので、本当はローカルビルドしたい
- ただし、DevContainer環境ではメモリリークでプロセス落ちした経験が多数ある
- なので、諦めてExpoクラウドビルドを使用しているのが現状。本当はローカルだけでサクサク解決したい。
- ホストマシンにjavaとか色々インストールしたくないし、実際に入っていないからDevContainerで開発しているという事情があります。
- adbなら、ホストマシンに入っています。
```

```

### 2. 開発中の動作確認は EAS Development Build のみで十分ですか？
- 動作確認はエミュレーターメインで十分ですが、システムテストと運用テストは実機でも行いたい。

### 3. ADR-002 (Turborepo) の検討結果と合わせて判断しますか？
- 本ドキュメントを参照してください。

## ADR-002-turborepo.md

### 1. 共有パッケージで管理したいものは具体的に何がありますか？（Zod スキーマ、型定義、バージョン番号、その他）
- 例に挙げられているものが中心です。バックエンド側はUIがないので、共有したいものはあまり多くはありません。

### 2. GitHub Actions で APK ビルドを実行する場合、Turborepo の Remote Cache を使いたいですか？
- コスト次第ではありますが、コスト抜きにしても、個人作成なので、リソースが分散しすぎるのは望ましくないです。

### 3. ディレクトリ構成の変更（`backend/` → `packages/backend/` 等）は許容しますか？
- 許容します。turborepoが必要であれば、です。

### 4. npm workspaces のみ（Turborepo なし）でも需要を満たせそうですか？
- 実質ビルド対象はアプリだけなので、Turborepoなしでも良いかなと思います。
- npm workspacesでOKです。

## /workspaces/BBCast/docs/database/detail-design.md

### 5. `users/{uid}` コレクション (Phase 3 新規)

```
### 5.4 `users/{uid}/analytics` — ユーザーアクション集計

単一ドキュメント（ドキュメント ID: `summary`）。Firebase 側で TTL・キャッシュ量・送信停止/再開を制御。

| フィールド名 | 型 | 説明 |
|-------------|-----|------|
| `downloadCount` | `number` | ダウンロード数 |
| `playCount` | `number` | 再生数 |
| `quizAttempts` | `number` | クイズ回答数 |
| `quizCorrectRate` | `number` | クイズ正答率 (0.0〜1.0) |
| `wordRegistrations` | `number` | 単語登録数 |
| `lastSyncedAt` | `Timestamp` | 最終同期日時 |
```
- ユーザーアクションの部分は、このドキュメントはこれはこれで必要ですが、各ドキュメント（episodeProgramなど）で内訳パラメータを作って管理したい
- 例えば「再生数」だったら、ユーザーの総再生数だけではなく、各エピソードの総再生数が分かるように
- そういう意味では、ユーザーアクション集計は、わざわざドキュメントを作らなくても、各ドキュメントの該当項目の集計で算出できると思っている
