# 開発方針の見直し

## 全体アーキテクチャ

### features/javaのDockerイメージへの組み込み
- 現状の`devcontainer.json`では`ghcr.io/devcontainers/features/java:1"` が`features`に定義されている
- ただし、実際のテスト環境の構築・パッケージのビルドは、easコマンドで実行予定
- 巨大なJavaイメージを開発環境に載せる必要性を再確認したい
- docs/adr/ディレクトリを作成し、議論の必要のあるトピックごとにADRファイルを作成し管理していく。

### turborepoの導入
- 著作権の関係上、アプリの配信しない。
- ただし、技術ポートフォリオとしてアプリ自体は公開する。GitHub Releaseで管理する。
- CI/CDパイプラインに載せる際に、Expoのクラウドビルドを毎回実施するわけにもいかないので、ビルド回数を抑制したい
- 前項のJavaイメージの廃止とこのturborepoの導入はトレードオフになると思っている
- Javaイメージを載せたとして、GitHubのCD環境でAPKビルドができるの可能か疑問は残るが、もしCDにAPKビルドを含めるなら、turborepoを導入したい

### ZODの導入
- TypeScriptの一貫したエコシステムを最大限に活用するため、ZODを導入する
- テストも、ユニットテストは各スプリントで、結合テストは毎スプリントで実行する

### 変数管理
- `database` `frontend` それぞれで、定数を管理するためのtsファイルを作成する
- 各スクプトファイルは、定数ファイルをインポートして利用する
- また、バージョン番号やフロント/バックエンド共通で利用する変数をルートディレクトリ一箇所で管理する方法も考えたい。
- CI/CDパイプラインでそれぞれのアプリ側にフロント/バック共通変数用の.envファイルを流し込むとか？

### CI/CDパイプライン
- メインブランチへのプッシュまたはPRマージで、フロントエンド側はFirebase関数のデプロイ、バックエンド側はビルドとGitHubReleaseの更新を行うところまでやりたい
- デプロイフェーズに移る前に、テスト関数を前実行し、問題がなかった場合にデプロイフェーズに移るようにする

## アプリ設計

### ユーザー認証
- Firebase AdminSDKによるGoogle SSO認証を導入する
- `react-native-credentials-manager` を実装する
- 将来的には、AppleIDによるSSO認証も追加したいが、iOSテスト環境がないので、リリース時はGoogleのみ

### ユーザーアクションの集計と管理
- 以下のデータを収集する。
    * ダウンロードしたプログラムやエピソード数
    * プログラム再生数
    * クイズ回答数、正答率
    * 単語登録
- リアルタイム性は必要ない
- むしろ、Firestoreの容量圧迫に繋がるのを避けるためにも、データ収集の実行管理はFirebase側で行えるのが理想
- データ送信させるさせない、データのアプリ側でのキャッシュ量とTTL、データ収集の停止と再開など

### カーステモード
- 各エピソード詳細画面でのダウンロード音源の再生機能とは別に、ダウンロード済みの音源全てをリスト表示し、ループ再生する機能を付ける（カーナビへのBluetooth接続再生を想定。一度再生ボタンを押せば、操作不要）
- カーステモードの要件は以下
    * 全てのダウンロード済み音源で再生リストを作成
    * 再生リストは、チェックボックスで任意の音源の再生対象とするか否かを決定できる
    * 再生リストは、プログラム名や配信日時などの条件で、再生対象をフィルターできる
    * 再生リストは、上記の方法で決定した再生対象ファイルを、任意の順番に並べ替えることができる
    * 上記の方法でカスタムしたプレイリストを、プリセットとして登録できる

### エピソード画面UI
- エピソードのスクリプト表示画面のUIは、メッセージングアプリのようなものを想定
- 基本的に2人のスピーカーが会話を行い、その途中にインタビューのようなものが挟まれる形式のエピソードが多い
- そのため、メインスピーカーの2人のスクリプトを、画面左右それぞれから出ている吹き出しで表示
- インタビュー等の、メインスピーカー以外の会話は、吹き出しではないViewで囲う

### スクリプト画面での文字列選択とカスタムコンテキストメニュー
- スクリプト画面では、長押しで表示コンテンツ（文字列）を選択できるようにする
- フローティング・コンテキストメニューにカスタム項目を追加し、「単語帳へ登録」機能を実装

### 単語帳機能
- マイ単語帳機能を実装する。
- アプリ内のフローティング・コンテキストメニューからの登録
- 自分で登録したい任意の単語の登録
- 登録する項目は、英単語、品詞、意味など
- 登録した単語は、ローカルとFirestore両方に登録する

### `react-native-pager-view`の導入
- Expo Routerのタブパネルに加え、画面スワイプでタブ切り替えができる機能を実装する

## その他最新機能の積極導入
- 本アプリはUXは一定水準満たされていればよく、それよりもポートフォリオとしての性格を有する
- そのため、積極的に最新の技術（安定版）を導入してゆく
- 本要件を満たすため、既存の設計を変更することも許可する

##  開発の進め方
- copilot用instruction.mdを作成する。以下の内容は、必ず盛り込む。
    * 基本設計書のフェーズごとに実装を進める
    * 各フェーズで詳細設計書を作成する。ただし、同一フェーズ内で詳細設計を分割する方が望ましい場合は、複数の詳細設計書を作成する
    * 逆に、従前のフェーズの機能に追加実装をする場合などは、従前の詳細設計書を更新する
    * 各フェーズの開始時に読み込む用の、全体の設計仕様とこれまでの経過をまとめた、copilot用の履歴ファイルのようなものを作成する
    * copilotは各フェーズ開始時に上記履歴ファイルを必ず読み込んでから実装計画に移る
    * copilotは必要なタイミングで上記履歴ファイルを更新する
    * 各フェーズの終了時、私が閉じる指示を出した際には、上記履歴ファイルを最新版に更新する。その際は、リポジトリ全体をスキャンし、相互矛盾や履歴ファイルとの乖離がないかを確認し、必要な修正を行う
    * copilotの判断では決定できない重要な設計方針については、ADRを作成し、私の指示を仰ぐ
    * その他、copilotの管理外（FirebaseやGCPコンソールなど）での操作が必要な場合は、docs/owner-tasks/ディレクトリを作成し、そこに目的と手順、一般的なトラブルシューティングを書き加えた.md形式の手順書を作成すること
